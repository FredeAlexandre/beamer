## Method

- **Media source** (`source.cpp`, own code following the VirtualCamera sample's design): `IMFActivate`
  (class factory object) -> `IMFMediaSourceEx` + `IMFGetService` + `IKsControl` -> one `IMFMediaStream2` +
  `IKsControl` with `MF_DEVICESTREAM_STREAM_CATEGORY = PINNAME_VIDEO_CAPTURE`,
  `MF_DEVICESTREAM_FRAMESERVER_SHARED = 1`, `MFFrameSourceTypes_Color`. Media types NV12 1280x720,
  1920x1080, 640x360 at 30/1. System-memory samples from `MFCreateVideoSampleAllocatorEx` (the D3D manager
  Frame Server offers is ignored). A worker thread delivers when a `RequestSample` is pending and a newer
  helper frame exists (woken by the helper's event), else a pattern/placeholder on a 33 ms clock.
- **Stamp**: every frame carries a 40x3 block code (counter, low 32 bits of wall-clock µs, origin =
  source pattern / placeholder / helper), decodable after scaling, RGB conversion and H.264. Latency =
  consumer's `GetSystemTimePreciseAsFileTime` (or JS `performance.timeOrigin + now()`) minus the stamp,
  same clock in every process on the PC.
- **Consumers**: `camprobe read` (synchronous `IMFSourceReader` from `MFEnumDeviceSources`, the path
  Chromium, Teams and the Camera app use), `ffmpeg -f dshow | camprobe yuvcheck` (DirectShow), `web/gum.html`
  in headless Chrome/Edge (`--headless=new --use-fake-ui-for-media-stream`, throwaway profile, real
  devices) run in Alex's session.
- **Helper stand-in** (`feeder`): runs in Alex's session (scheduled task, normal token, like Beamer),
  waits for demand, writes stamped frames (pattern, or a decoded H.264 file) into the ring. CPU from
  `QueryProcessCycleTime` (scaled by the nominal clock) and `GetProcessTimes`; Frame Server CPU from its
  svchost (`svchost -k Camera`, the FrameServer service PID).
- **H.264**: test streams from the MF encoder (ffmpeg `h264_mf`, software, CBR, High, `-bf 0`, GOP 60:
  720p 3.2 Mbit/s, 1080p 6.2 Mbit/s, 300 frames, `has_b_frames=0`), plus C1's committed VideoToolbox
  recordings. Decoder `CLSID_CMSH264DecoderMFT`, NV12 out, `MF_LOW_LATENCY` + `CODECAPI_AVLowLatencyMode`;
  hardware = `MFT_MESSAGE_SET_D3D_MANAGER` with a D3D11 video device; input paced at 30 fps; latency =
  `ProcessInput` -> NV12 in system memory.
- Runs 10-12 s each unless noted; SSH runs are session 0 (elevated), "in session" runs are Alex's session 1
  through a temporary scheduled task (`scripts/in-session.ps1`).

- Consumer `ActivateObject` usually 11-15 ms; once 1.0 s (Frame Server cold, just restarted) and once

## Q3: on demand

Sequence seen by the source when an app opens and closes the camera: `ActivateObject` (once; Frame
Server keeps the source) -> `Start` with the chosen type -> samples -> `SetStreamState(STOPPED)` ->
`Shutdown`, after which Frame Server re-creates and shuts down the source 2-3 times within ~60 ms (each one
republishes "stopped"; harmless, the helper must treat repeated stops as idempotent).

Signal path: the source writes `streaming`, `want_w/h`, a sequence number and a timestamp into the shared
header and sets `Global\...Demand` (an auto-reset event created by the helper with a DACL that lets
LocalService modify it). The helper waits on it.

| Event | Latency to the helper |
|---|---|
| source Start -> helper sees "streaming" | 0.01-0.11 ms (10 runs) |
| app's first `ReadSample` -> helper | 0.47 ms (720p), 0.67 ms (1080p) |
| app's first `ReadSample` -> first frame in the app | 1.3-2.3 ms (source pattern until the helper's first frame) |
| app releases the reader -> helper sees "stopped" | 0.36 ms |
| app killed (`Stop-Process -Force`) -> helper | 13 ms |

The Mac cold start (C1: camera start + 150 ms encoder + 37-56 ms first IDR, plus the link) dominates; the
source shows a placeholder until the first real frame.

## Q4: frames from the user session into the source

Design that worked: the **source creates** `Global\BeamerCamC2.Shm` (9.3 MB: header + 3 NV12 slots of
1920x1080) and `Global\...Frame` (auto-reset) when activated, DACL `SY, LS, BA, IU` full access; the
helper opens them when signalled. The helper writes slot `latest+1` under a per-slot seqlock, then
publishes `latest` and sets the frame event; the source copies the newest slot into the sample when a
request is pending (copy re-checked against the seqlock). Holding the section open in the helper keeps it
alive across source re-creations. Alex's normal token lacks SeCreateGlobalPrivilege (`whoami /priv`),
and the source's own attempt from a user process fails with error 5, so the section cannot be owned by
the helper; `Global\` events need no privilege.

- CPU for "SW, session 1" is from cycles; `GetProcessTimes` under-reads there (2 %), as the audio work found.
- **Hardware decode is 2-3x faster in Alex's session than in session 0** (1.8 vs 4.1 ms at 720p, 2.8 vs
  6.3 ms at 1080p, same code); the helper runs in the session, so the session numbers apply. Most of the
  hardware time is the wait for the GPU in the readback (`Map`), not CPU.
- **LTR loss recovery (C1's request)**: `synth_720p30_ltr_recovery_6s.h264` decoded fully, then without
  access units 90 and 91, luma compared frame by frame. SW and HW identical: frames 92-93 PSNR-Y 14.1 dB
  (garbage), **frame 94 onward bit-identical** (`clean_from 94`), 0 decode errors in both runs. So the
  decoder does **not** signal the missing references: the receiver must detect loss itself (C3's sequence
  numbers) and hold the last good frame until the recovery frame instead of showing what the decoder outputs.
- **Format**: NV12 out of the decoder, NV12 into the camera. No consumer needed another source format: MF
  apps get conversion from the source reader, the DirectShow bridge adds YUY2 itself, Chrome/Edge took
  NV12. The source does not need YUY2/MJPG (a `formats=nv12,yuy2` switch exists in the prototype if an app
  turns out to need it).
- **Decode in the helper, not in the source**, because: (1) the source runs inside the shared Frame
  Server svchost; a decoder or driver crash there takes down every camera on the PC, a helper crash only
  ours (and the source falls back to the placeholder); (2) the helper already has the network side (C3)
  and the Mac protocol, loss detection, and the "hold last good frame" decision belong next to them; (3)
  the source stays tiny, with no network, crypto or decoder state, which keeps the part that needs admin
  to update small and rarely changed; (4) the cost of crossing the process boundary as NV12 is 0.1 ms write
  + 0.5-1 ms delivery and 0.5-1 % CPU in Frame Server. Decoding in the source could keep frames on the GPU
  (Frame Server offers a D3D manager) and save the readback, but nothing here needs it.

## Q6: robustness

| Case | What happens | Measured |
|---|---|---|
| Two apps at once | First app (720p) keeps streaming (30.08 fps, 0 gaps); the second gets `ReadSample` = `0xC00D3704` (`MF_E_HW_MFT_FAILED_START_STREAMING`) whether it keeps the type or asks 1080p. Same as a physical camera with the default settings | The source never sees the second app |
| App killed while streaming | Frame Server stops the stream; the next app opens at once | stop at the helper 13 ms after the kill; new app 30.33 fps, 0 gaps |
| Helper killed while an app streams | The app gets no new sample for 0.5 s (it keeps showing the last frame; 26 fps that second), then the placeholder at 30 fps; real frames return when the helper writes again | placeholder 496 ms after the kill (threshold 500 ms in the prototype); helper restart -> real frames when it writes; 0 errors in the app |
| Helper output 720p <-> 1080p every 3 s | No gap, no stall, no error; the source scales to the app's type (nearest neighbour) | app at 720p: p50 1.34 ms (vs 0.5); app at 1080p fed 720p: p50 3.61 ms, one 58 ms outlier |
| Session camera's creator exits mid-stream | App's `ReadSample` fails `0xC00D3EA2`; camera gone | (System lifetime avoids this) |

**Placeholder recommendation**: always deliver something at 30 fps. Before the first real frame and when
real frames stop for more than ~250 ms (prototype: 500 ms), deliver a static "Beamer Camera: waiting for
<Mac name>" image (dark grey, logo, small moving indicator so it does not look frozen), baked into the
DLL. Never black (looks like a broken camera) and never the frozen last frame for long (looks like the
person froze).

## Risks

- **Admin at install.** The CLSID must be in HKLM and the DLL outside the user profile; Beamer's installer
  is per-user (`PrivilegesRequired=lowest`). Phase 2 needs a one-time elevated step, like VB-CABLE.
- **Updating the DLL**: Frame Server keeps it loaded while any of our sources exists. Replacing it in place
  needs the FrameServer service stopped (admin); use a versioned path per release instead.
- **Second app refused** unless the user enables Windows' multi-app toggle for the camera (untested here).
- **Smart App Control / WDAC**: unsigned DLL loads here because SAC is off; on a PC with SAC on, the DLL
  (loaded into a Windows service) probably needs a trusted signature. Untested.
- **Consumer consent**: packaged apps (Camera, Teams) ask once per app; the first call fails silently
  until the user answers. Desktop apps (Chrome, Discord) follow the "desktop apps" switch, Allow here.
- **The `(Caméra virtuelle Windows)` suffix** is shown in every app's camera list.
- **Silent decoder corruption** after loss (Q5): must be handled by the receiver.
- **IPC DACL** in the prototype grants all interactive users; on a multi-user PC another logged-on user
  could read the frames. Phase 2 should restrict to the camera owner's SID (below).
- **Untested**: logoff/reboot survival, sleep/resume, fast user switching, GPU driver reset (helper must
  fall back to software decode), Teams/Zoom/Discord, an app that changes resolution mid-stream
  (`applyConstraints`), Windows Hello / Studio Effects interplay.

## Recommendation for Phase 2

**Components and process boundaries**

| Component | Runs in | Job |
|---|---|---|
| `BeamerCameraSource.dll` (C++17, ~1 kloc) | Frame Server (`svchost -k Camera`, LocalService) | The media source: NV12 1280x720 / 1920x1080 / 640x360 @ 30 (add 640x480 / 1280x960 only if an app needs 4:3); creates the ring + frame event; publishes Start/Stop/type; delivers the newest frame per request; placeholder. No network, no decode, no crypto. |
| `beamer-camera.exe` (C++17, next to `beamer-audio.exe`, same `build-win.cmd` toolchain, JSON-lines stdio like the audio helper) | Alex's session, child of Beamer | `install` / `uninstall` verbs (elevated, once); at start: create/`Start` the System/CurrentUser camera (idempotent, 28 ms, no admin), create the demand event; on demand: tell Beamer `{"ev":"camera_demand","on":true,"w":1280,"h":720}`; receive H.264 access units (from Beamer over stdin, or directly from C3's transport), detect loss, decode (MF, D3D11, low-latency, SW fallback), hold the last good frame until recovery, scale to the app's size only while the Mac has not switched yet, write NV12 into the ring. |
| Beamer (Python) | Alex's session | Starts the helper, relays demand to the Mac (camera on only while `streaming`), routes the video stream, UI (install button, status: "in use by an app", placeholder state). |

**IPC (as prototyped, with two hardening changes)**

- Section + frame event created by the source in `Global\` (only the service can create the section).
  Demand event created by the helper. Names carry a per-install GUID: `Global\BeamerCamera.<guid>.{Shm,Frame,Demand}`.
- DACL: SYSTEM, LocalService, and **the owner's SID only** instead of INTERACTIVE. The installer writes the
  owner SID and GUID into `HKLM\SOFTWARE\Beamer\Camera` (admin step), the source reads them there.
- Header versioned (`magic`, `version`), seqlocked slots, `latest`, consumer state (`streaming`, `want_w/h`,
  `state_seq`), counters (delivered, placeholders, dropped). Helper treats repeated "stopped" as one.
- Placeholder after 250 ms without a real frame, and from Start until the first real frame.

**Install / registration**

1. Elevated, once (UAC prompt from Beamer's camera page, like VB-CABLE): `beamer-camera.exe install`
   copies the DLL to `%ProgramFiles%\Beamer\Camera\<version>\BeamerCameraSource.dll` (readable by
   LocalService through Users), writes `HKLM\Software\Classes\CLSID\{...}\InprocServer32` (path,
   `ThreadingModel=Both`) and `HKLM\SOFTWARE\Beamer\Camera` (owner SID, GUID). **Needs admin.**
2. Unelevated, every helper start: `MFCreateVirtualCamera(SoftwareCameraSource, System, CurrentUser,
   "Beamer Camera", CLSID)` + `Start`. **No admin.** The camera stays when Beamer exits (apps keep it in
   their list and see the placeholder "Beamer is not running").
3. Update: a new version directory + re-point the HKLM path (admin again, or have step 1 install a tiny
   always-elevated updater; decide in Phase 2). Old DLL unloads when Frame Server idles.
4. Uninstall: helper `Remove()`s the camera (no admin), then elevated: delete the HKLM keys and the
   directory (stop FrameServer if the DLL is still loaded).
5. Packaging: `beamer-camera.exe` and `BeamerCameraSource.dll` built by `native/camera/build-win.cmd`,
   shipped next to `beamer-audio.exe` (PyInstaller data files); the DLL is only copied to Program Files by
   `install`. Sign both with the release identity when one exists (SAC/WDAC risk above).

**Latency budget on the PC side** (measured): decode 1.9 ms (720p) / 3.1 ms (1080p) hardware + ring and
Frame Server 0.5 / 0.9 ms + the app's own pipeline (Chrome 2.3-2.8 ms to its frame callback; DirectShow
apps ~33 ms extra). The PC adds **about 3-5 ms** for MF/browser apps.

`SWD\VCAMDEVAPI*` device (present or not), no `C:\ProgramData\BeamerCamC2`, no `C2-*` scheduled task, no
`feeder`/`camprobe`/`vcamctl` process; the FrameServer service was left stopped (demand-start, as at the
start). Beamer and its tasks were not touched. What stays: the work folder `C:\Users\Alex\camera-c2\`
(binaries, scripts, the H.264 test streams and C1's recordings under `media\`, `source.log`, `run\`
outputs; the 1.3 GB raw YUV files were deleted). Remove it with `Remove-Item -Recurse
C:\Users\Alex\camera-c2` when Phase 1 is closed.

If Needs Alex 1 is run, undo it with (elevated):

```powershell
powershell -ExecutionPolicy Bypass -File C:\Users\Alex\camera-c2\cleanup.ps1
```

which does: `vcamctl remove system user` (the device), `vcamctl unregcom hklm` / `hkcu` (deletes
`HKLM\Software\Classes\CLSID\{EF41A4B9-7102-4C33-A218-3AF46FED9B0D}`), removes `C2-*` tasks, stops the
helpers, stops the FrameServer service (unloads the DLL), deletes `C:\ProgramData\BeamerCamC2`, and lists
any remaining `SWD\VCAMDEVAPI*` device (expect none). If the multi-app toggle was turned on, it disappears
with the device.

Sources for the multi-app toggle: [Pureinfotech](https://pureinfotech.com/allow-multiple-apps-use-camera-windows-11/),
[Eleven Forum](https://www.elevenforum.com/t/enable-or-disable-multiple-apps-to-use-camera-in-windows-11.31199/).
