## Method

- `build/beamer-camera` (ObjC++, `src/`), universal, ad-hoc signed with the hardened runtime and the
  camera entitlement. Synthetic source: NV12 frames generated at 30 fps on a `mach_wait_until` clock. The
  content is a moving gradient, a moving textured disc, a scrolling text-like panel and ±3 luma-step
  temporal noise. The frame number and host capture time are written into a code strip on the top rows
  (format in the README).
- Encode time = `VTCompressionSessionEncodeFrame` call -> output callback (host clock). That includes the
  XPC round trip: VideoToolbox runs the encoder in a `VTEncoderXPCService` process spawned per client.
  CPU = our own `getrusage`, minus the pattern generator's thread time, plus the CPU-time growth of
  `VTEncoderXPCService` / `VTDecoderXPCService` sampled by `experiments/runner.py`. All figures are % of
  one core.
- Quality: every frame is decoded back in-process (`VTDecompressionSession`, synchronous) and compared
  with a copy of its source (PSNR-Y and PSNR-UV, whole frame). Loss: frames are withheld from that
  decoder. A simulated receiver acknowledges an LTR token only for frames it decoded cleanly, N frames
  later (an RTT).
- Independent check: `experiments/check_stream.py` decodes the Annex-B with ffmpeg (libavcodec), reads
  the code strip of every frame and compares it with the trace. With `--drop` it also decodes a copy with
  those frames removed and compares each frame with the full decode.
- Runs: 20 s per configuration unless noted, one at a time, on mains power, with Beamer and the usual
  apps running. The rough numbers in `out/` (gitignored) come from `runner.py` JSON lines.

## Q3: VideoToolbox H.264

### Encoder selection

| session | encoder chosen | hardware |
|---|---|---|
| default (no spec) | `com.apple.videotoolbox.videoencoder.ave.avc` "Apple H.264 (HW)" | yes |
| `EnableLowLatencyRateControl` | **`com.apple.videotoolbox.videoencoder.h264.rtvc`** (not in the public encoder list) | yes: still chosen with `RequireHardwareAcceleratedVideoEncoder`, 1.5-2.5 % CPU in total. It does not implement `UsingHardwareAcceleratedVideoEncoder`, so that query returns nothing |
| forced `...videoencoder.h264` "Apple H.264 (SW)" | software | no: 46 % CPU, 436 ms latency |

The rtvc session uses `EnableLTR = 1` by default and one temporal layer. Its supported-property list also
names private keys (`PeriodicRefreshMode`, `MaxRefreshFrameIntervalDuration`, `RequestedMaxEncoderLatency`,
`EnableFrameDropping`, `NumberOfSlices`, ...). `MaxFrameDelayCount` returns -12900 (not supported) in
low-latency mode, which has no frame delay anyway. The macOS 26 `VideoConferencing` preset is only
`{AverageBitRate 6000000, EnableLTR 1, RealTime 1}`, nothing new.

Rate/quality points (10 s, low latency, verify): 720p at 1.0 Mbit/s 980 kbit/s, PSNR-Y 39.3 mean, IDR
79.6 KB; 720p at 5 Mbit/s PSNR 41.5, IDR 193 KB; 1080p at 2.5 Mbit/s PSNR 40.0, IDR 187 KB. The ±3-step
synthetic noise caps PSNR near 41-42 dB (the encoder rightly drops it), so read these as a sanity check
(decodes, no drift, no artefacts) and not as camera quality. The max encode time is always frame 0 (the
IDR right after session creation). Afterwards the tail is under 9 ms (p99). No frame was dropped by the
encoder in any run.

Readings:
- **Low latency vs the default HW session**: same encode time. The low-latency mode has steadier rate
  control (1 s sd 31 vs 163 kbit/s), no periodic keyframes (the default HW session puts an IDR every 1 s,
  155 KB, which costs 5 dB PSNR at 2.5 Mbit/s), and supports LTR. Software is unusable (436 ms).
- **IDR cost**: 120 KB at 720p (about 12 average P-frames, 0.39 s of channel time at 2.5 Mbit/s); 256 KB at
  1080p. After a forced IDR the rate control pays the debt: the next P-frames shrink to 0.5-3 KB and
  PSNR stays 2-5 dB lower for about 10 frames. The 200 ms window holding an IDR reaches about 2x the
  target rate.
- **Bitrate changes live**: `AverageBitRate` set at frame 120 (2.5 -> 1.0 Mbit/s) and at frame 240 (back
  to 2.5): the very next 200 ms window was at 517 then 1048 kbit/s, and later 2860 then 2449. The encoder
  follows within one window, so congestion control can drive it directly.
- **Constrained High vs Constrained Baseline**: same PSNR, Baseline IDR +13 %. ffprobe sees Constrained
  High as High, level 3.1 (720p) / 4.0 (1080p), no B-frames, CABAC.

### Loss and recovery (720p 2.5 M low latency, 8 s runs, `--verify-drop`)

Each frame is a reference (dropping any single frame, small or large, corrupts every later frame).
The frames also stay corrupt: there is no GOP, so nothing heals by itself.

| loss, then | recovery frame | PSNR-Y of recovery frame / next frames | note |
|---|---|---|---|
| frame 100 lost, nothing | none | 14 dB for the rest of the run (> 4 s) | infinite GOP |
| frame 100 lost, `ForceKeyFrame` at 103 | IDR 120,106 B | 38.6 / 36-38 for ~10 frames | rate debt: P-frames 0.5-3 KB |
| frame 100 lost, `ForceLTRRefresh` at 103, acks after 3 frames (100 ms) | P 14,211 B | **41.4 / 41.2-41.4** | heals at once, no rate debt |
| same, frame 150 lost, refresh at 153, ack after 3 frames | P 14,884 B | 41.4 | |
| ack after 10 frames (333 ms) | P 12,038 B | 41.2 | |
| ack after 45 frames (1.5 s, the worst Wi-Fi stall) | P 37,538 B | 40.7 / 40.4-41.0 | older reference costs more |
| never acked | I (non-IDR) 119,802 B | 38.6 | the encoder falls back to intra |
| 1080p 5 M, ack after 3 frames | P 20,282 B | 41.2 | IDR would be 256 KB |
| periodic refresh `MaxRefreshFrameIntervalDuration=1` (private key) | non-IDR I-frame of 120-125 KB every 30 frames | heals within 1 s; PSNR saw-tooth 36-41 | **not** gradual intra refresh |
| private `PeriodicRefreshMode` = 1 or 2 | rejected (-12902) | n/a | no gradual intra refresh |

The committed clip `synth_720p30_ltr_recovery_6s.h264` (frames 90-91 lost, LTR refresh at 94) decoded by
**libavcodec without frames 90-91 is bit-exact with the full decode from frame 94 on**. Only 92-93
differ (12.8 dB), so standard H.264 long-term references work in a third-party decoder. C2 must confirm
the same with the Windows decoder (Media Foundation).

## Risks

1. **Camera numbers missing** (Q1 cold start, Q2, Q4, Q5 in practice): one permission click away
   (Needs Alex). Until then the latency budget has an unknown capture term. The encoder adds 5 ms.
2. **LTR depends on the PC decoder** handling long-term references and on a feedback path. Feedback means
   per-frame receipt acks plus a "decoder broken since frame N" message. Fallback is a forced IDR
   (120/256 KB burst). Without feedback, LTR still yields intra frames after a refresh request.
3. **`h264.rtvc` is not in the public encoder list** and its private keys are undocumented. Use only the
   public API (`EnableLowLatencyRateControl`, `EnableLTR`, `ForceLTRRefresh`, `AcknowledgedLTRTokens`,
   `ForceKeyFrame`, `AverageBitRate`). Do not use `MaxRefreshFrameIntervalDuration`.
4. **IDR bursts** of 120-256 KB in one frame: the transport must pace them (C3), or use LTR so they are
   rare (start, new receiver, size change, no-ack fallback).
5. **Low light** may halve the frame rate (15 fps) unless pinned.
6. **Video effects** are applied by macOS at the user's choice. Reactions are on by default and cannot be
   switched off by Beamer: a stray gesture is avoided with the Info.plist default, but a reaction picked
   from the menu still shows on the PC.
7. Synthetic PSNR is not camera quality; real-camera rate/quality at 2.5 Mbit/s is unmeasured.

## Recommendation for Phase 2

- **Language**: ObjC++ (`.mm`) for the Mac capture/encode backend, as for `native/audio/mac`.
  AVFoundation and VideoToolbox are ObjC/C; the code lives in the same clang++ build as the C++17 engine
  and is easy to share with the C++ transport and packetizer. This prototype's `encode.mm`/`capture.mm`
  can be lifted almost as is.
- **Where**: inside the existing helper, as a video backend of the same engine (`camera_mac.mm`,
  `videoenc_mac.mm` next to `tap_mac.mm`), not a new `beamer-camera` executable. Reasons:
  - the video stream must use the same UDP flow, AEAD keys, probing/hole punch, receiver reports and
    TCP-link fallback that the engine already has per peer;
  - one process can schedule audio ahead of video on that flow, so a 120 KB IDR does not delay a 20 ms
    audio packet;
  - the TCC attribution is identical either way (Beamer.app is responsible for any helper it spawns);
  - crash isolation from video is mostly given already: the encoder runs in Apple's `VTEncoderXPCService`.

  A camera stream is just a new `send` kind (`"camera"`, with size/fps/bitrate), started when the PC asks
  (the PC app opened Beamer Camera) and stopped on `stop`. The helper is already running, so a request
  costs only camera start + encoder create (150 ms) + first IDR (37-56 ms). Revisit if C3 finds video
  needs a separate flow; a second flow can still live in the same process. If Phase 2 renames the
  helper (`beamer-media`), do it once for both.
- **Capture**: the 1280x720 or 1920x1080 `420v` format by size, `activeVideoMinFrameDuration` 1/30 (pin
  the max too if the low-light test shows 15 fps drops), output 420v, the `CVPixelBuffer` (IOSurface) handed
  straight to VT. Use `alwaysDiscardsLateVideoFrames`. Observe `inUseByAnotherApplication`, the effect flags
  and session interruptions, and report them as events.
- **Encode**: `kVTVideoEncoderSpecification_EnableLowLatencyRateControl = YES` (+
  `RequireHardwareAcceleratedVideoEncoder = YES`, so a software fallback with 436 ms latency fails instead of
  being used); `RealTime = YES`, `ExpectedFrameRate = 30`, `AllowFrameReordering = NO`,
  `ProfileLevel = H264_ConstrainedHigh_AutoLevel` (switch to Constrained Baseline only if C2's decoder
  needs it), `AverageBitRate` 2.5 / 5 Mbit/s and adjusted live by congestion control, `EnableLTR = YES`.
  Leave out `MaxKeyFrameInterval`, `DataRateLimits`, presets and `PrioritizeEncodingSpeedOverQuality` (no
  measured effect).
- **Recovery protocol** (for C3 to confirm): the receiver acks received-and-decoded frames by frame number
  (sequence). The sender maps frame numbers to `kVTSampleAttachmentKey_RequireLTRAcknowledgementToken`
  values (tokens never travel) and passes them in `kVTEncodeFrameOptionKey_AcknowledgedLTRTokens`. On a
  loss report, `ForceLTRRefresh` (12-38 KB). On a second report while no ack has arrived for ~1 s, or on a
  decoder error, `ForceKeyFrame`. Always IDR at stream start, when a receiver joins, and when the size
  changes. Annex-B with SPS/PPS in front of every IDR.
