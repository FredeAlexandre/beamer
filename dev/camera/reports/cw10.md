## What it does (§4.9)

On the PC (T), for each video recv stream, every 50 ms helper tick:

- **video input**: `video_present_delay` without the hold = `enc_delay` (newest completed frame with a time
  map) + D + 2 ms source delivery, only while the stream is live (started, presenting, time map and offset
  known); plus the offset value the stream maps with (flow estimate, else the provisional one).
- **audio input**: the mic recv stream **on the same flow** (same sender, same clock, same offset) that
  renders **into the virtual mic** and has a time map (`sr`): `audio_present_delay` = render time of the
  sample being rendered - (its sender capture time from the stream's time map - offset) + the render path
  latency (CABLE, per mode). Same offset value as the video, so the offset error cancels in the difference.
  Nothing else gives an audio input: no mic forwarded, a mic from another machine (another flow), a mic
  rendered to a speaker, a mic without a time map.
- **policy** (`LipSyncPolicy`, pure, explicit time): EWMA (2 s) of `audio - video`; target = clamp(0, 150)
  only once both inputs have been present for 2 s without interruption; the applied hold moves toward the
  target by at most 10 ms/s (also back to 0 when an input goes away; the warm-up restarts when it comes back).
  Audio is an input only: nothing in the audio path reads the policy.
- **presenter**: the existing CW2 hook (`LipSyncHold`, now one per video recv stream) adds the hold to every
  present time (and to the backlog bound). Dev override `sync_offset_ms` n (0..150) forces the hold;
  `null` gives the policy back (it kept running meanwhile).
- **CABLE render path latency per mode** (`cable_render_path_ms`, constants from audio WP12, lebig): shared at
  the low-latency 128-frame period 67 ms (59-72, 300 s p50 69.2), shared at the default 480-frame period
  110 ms (102-117), exclusive 38 ms (35.9; WP4 43-45). The Windows backend reports the mode **actually opened**
  (exclusive can fall back to shared; the low-latency period can be refused) through the new
  `StreamHandle::render_path_ms()`; dev key `sync_audio_path_ms` n (0..300, `null` = the backend's) overrides
  it for measurement.
- **stats** (video recv stream): `sync_ms` (applied hold), `sync_audio_ms` (audio_present_delay, null when no
  paired mic), `sync_skew_ms` (smoothed audio - (video + hold): positive = audio later, negative = audio leads
  and nothing is done), `sync_path_ms`, `sync_override`; `video_present_delay_ms` now includes `enc_delay`
  (was D + hold + 2).

## Contract issues

1. **Test hunks outside §2.2/§12**: `engine_tests.cpp` needs a 3-line hunk (declare and append
   `sync_test_cases()`), like CW2's video list; §12 named only `build-tests.*`.
2. **`backend.h` + `backend_win.cpp` hunks** (not listed for CW10): the render path latency has to come from
   the client actually opened (exclusive falls back to shared, the low-latency period can be refused), which
   only the Windows backend knows. `StreamHandle::render_path_ms()` is virtual with a default (-1), so the Mac
   and null backends are untouched. Not compiled yet (PC off).
3. **Pairing rule made explicit**: "the active mic stream from S into its virtual mic" = a `mic` recv stream on
   the **same flow** as the video with `sink.virtual_mic` and a received time map. A machine never has two
   (one mic route); if it had, the first one with data wins.
4. **`sync_offset_ms` semantics**: CW2's hook treated 0 as "no override"; now 0 forces no hold (useful for
   measuring), `null` returns to the policy. `video_present_delay_ms` (stats) now includes `enc_delay`, as §4.9
   defines it.
5. **Clock domain on the Mac sender (to verify on the first live run)**: the audio time map is stamped by the
   engine (`steady_clock`), the video time map and the code strip by the Mac backend (`mach_absolute_time`,
   "host clock == now_ns()" in `synth_mac.mm`). The policy needs them to be one clock. libc++'s `steady_clock`
   on Apple should be `CLOCK_UPTIME_RAW` (= `mach_absolute_time`); on this Mac (no sleep since boot) they read
   identical, but that cannot show whether sleep time is counted (`lldb` was not allowed here). If they
   differed, every hold would be off by the Mac's total sleep time (clamped to 0 or 150). `cam_lipsync`
   checks it on every run (`audio_source_check.clock_same_domain`, helper `now_ns` vs the app's monotonic
   stamp) and reports it.
6. **Audio capture time = when the sample entered the engine** (CW2 contract issue 14 kept): the Mac mic's
   device input latency (a few ms) is not in the audio time map, so a real mic is held a few ms short. The test
   source has none, so `cam_lipsync` is not affected; `cam_lipsync_real` will show it.
7. **`cam_lipsync` PC side**: §4.9 says "one `pcside.py` run". `dev/audio/e2e/pcside.py` can only start `gen |
   play` pipes in Alex's session, so the case carries its own PC half (`cam_lipsync.py pcside` / `agent`, same
   scheduled-task trick, `tap.py` for CABLE Output). Every record is still on the PC's QPC clock; camprobe's
   wall-clock frame times are mapped to QPC by pairs sampled beside it every 250 ms. CW11's `preflight.py`
   already looks for `cam_lipsync.py`; CW11's `all` can call `cam_lipsync.py run` (exit code 0 pass-through,
   2 = stopped with a reason, result in `runs/cam_lipsync/<name>/result.json`).
