## Method

- **Chain** (all in `proto/e2e/`):
  - **Mac `camsend`** (ObjC++, new, always running). It compiles in C1's synthetic source (`synth.mm`: frame
    number + Mac capture time in the code strip) and C1's VideoToolbox settings (low-latency rate control, hardware
    required, Constrained High, no reordering, LTR). It starts a stream when the PC sends `kStart` and stops it on
    `kStop` (or after 3 s without a receiver report).
  - **Mac sender policy (C3's):** 36 B header + ≤ 1148 B fragment + 16 B zero tag (≤ 1200 B). P/LTR frames go
    through a 32-packet / 25 Mbit/s token bucket, IDRs are paced at k x bitrate, retransmissions go first, from a
    1 s history.
  - **Real feedback:** `kRR` every 10 ms carries the newest cleanly decoded frame and the start of the current
    clean run; the Mac turns the frames in that run into `AcknowledgedLTRTokens`. `kNack` asks for the identical
    bytes again. `kPli` -> `ForceLTRRefresh` (IDR only with no acknowledged token, or after 3 refreshes for the
    same loss).
  - **PC `camrecv`** (C++, new) runs in Alex's session (scheduled task, normal token). It waits on C2's demand
    event and source header, sends `kStart`/`kStop`, and reassembles. It NACKs holes ≤ 64 packets at once (then
    every max(4 x RTTmin, 15 ms), 3 tries) and decodes in order with C2's MF decoder (D3D11, `AVLowLatencyMode`,
    staging readback). A frame not repaired by its deadline (or a hole > 64 packets) -> PLI, and the receiver
    keeps decoding but shows nothing until an IDR / LTR refresh newer than the lost frame. Each shown frame is
    written into C2's ring at its playout deadline: adaptive D = p99 of the last 10 s of completion delays + 8 ms
    in [50, 150] ms, measured from encoder output. IDRs and frames that miss the deadline are shown as soon as
    they are decoded (see "Changes").
  - **Virtual camera:** C2's media source DLL and registration, unchanged (copied from `camera-c2\bin`).
  - **Consumer:** headless Chrome 157 `getUserMedia` on `web/gum4.html` (C2's page reworked). It reads C1's code
    strip on every `requestVideoFrameCallback`, or classifies the frame with C2's stamp (pattern / placeholder),
    or counts it unreadable.
- **Integrity check, two independent ones:**
  - the browser checks every delivered frame's strip: sync, checksum, frame number in order, and the strip's time
    equal to the Mac log for that frame;
  - an oracle thread in `camrecv` regenerates C1's synthetic picture for the frame number and computes PSNR-Y of
    every frame written to the ring. Clean frames measure 36.6-41.4 dB; C1/C2's corrupt frames measured 14 dB;
    the threshold is 30 dB.
- **Clocks:** pings every 200 ms; per 5 s the lowest-RTT one; a linear fit maps Mac host ns to PC system time
  (drift -6.5 to +0.9 ppm, residual ≤ 1.3 ms).
  - **Surprise:** Chrome's `performance.timeOrigin + now()` drifts **-25 ppm** against Windows system time (-15 ms
    in 10 min; C2 only ran 10 s). The page logs `Date.now() - (timeOrigin + now())` every 10 s (every cycle in Q2)
    and the analysis corrects every browser time with a linear fit. Uncorrected, the "virtual camera + Chrome"
    stage seemed to grow from 2.4 to 16 ms over 10 min.
- **Stages per frame**, joined by frame number:
  - encode = encoder output - capture;
  - pacing = last packet sent - encoder output;
  - network = last packet arrived - last packet sent (mapped);
  - queue = decode start - frame complete;
  - decode;
  - hold = ring write - decode end;
  - vcam+app = Chrome frame callback - ring write.

  "Total" is measured directly (Chrome callback - capture), not summed.
- **Loss injection** on the receiver, before any processing, timed from the first video packet: drop the next N
  video packets (1, 5, 30, 80), or every packet of any type for 1.5 s; 5 rounds each.
- **CPU:**
  - PC: `camrecv` self-reports process cycles (QueryProcessCycleTime / nominal MHz) and the oracle thread's
    cycles separately; the oracle is test-only and is subtracted below. A sampler (elevated, over SSH) samples
    Frame Server and Chrome.
  - Mac: `camsend` reports getrusage minus the synthetic generator's thread time (a camera has no such cost),
    plus `ps` of `VTEncoderXPCService`.
- **Traffic:** ≤ 5.2 Mbit/s of video plus 64 kbit/s audio-like, ports Mac UDP 40160 / PC UDP 24860 (outside
  24823-24830 and C3's). The PC punches first and the Mac sends from a connected socket: no firewall rule and no
  dialog on either machine (the Mac application firewall is on).

- **Encoder start is not the bottleneck while the process stays alive.** Only the very first session after
  `camsend` started cost 163-168 ms (C1's 150 ms cold create). Every later one took 2.5-13 ms, because
  VideoToolbox keeps `VTEncoderXPCService` warm. A Phase 2 helper that lives with Beamer gets the warm case.
- **The paced IDR is the largest term** (160 ms at 2.5x, 100 ms at 4x, 120 KB). At 1080p (256 KB) it is ~170 ms at
  2.5x and 107 ms at 4x (measured in Q3). Q3 shows 4x is safe. A real camera adds its cold start, unknown (C1 blocked; typically
  0.2-0.8 s for a built-in camera). So expect ~0.5-1.1 s in practice, with the source's pattern / placeholder on
  screen meanwhile.
- **Stop** costs ~20-30 ms of encoder flush and invalidation on the Mac; the network part is ~3 ms.
- Chrome's first displayed Mac frame is often not the IDR itself (8 of 20 at the start). The P-frames queued
  behind the IDR arrive within ~10 ms of it, and the source hands Chrome the newest slot. That is harmless.

## Q5: lip sync (pointer)

| path (p50, one way, to a PC app) | measured | with camera / mic front end |
|---|---|---|
| video, Mac camera -> Chrome (this report) | 57 ms from a synthetic source | + 25-70 ms camera (assumed) = **82-127 ms** |
| audio, Mac mic -> PC app via CABLE, shared (WP16 d_1) | **172 ms** from a test source | + a few ms of mic ADC |
| audio, same, low-latency switch (WP16 d_ex1) | **120 ms** | |
| **video ahead of audio** | shared: **45-90 ms**; low-latency: **-7 to +38 ms** | |

- Apps on the PC (Teams, Zoom, browsers) take the virtual camera and the virtual microphone as two live sources
  and do not re-align them, so this offset is what the far end sees (plus its own processing).
- With the low-latency microphone the two are within ±40 ms: fine. In shared mode, audio trails the picture by
  45-90 ms: at or beyond the EBU R37 limit (60 ms), under the ~125 ms where most viewers notice.
- **For Phase 2:** the PC helper knows both paths, because C3's `kSr` maps both streams to Mac capture time. Delay
  video (raise its playout target) by `audio_latency - video_latency` when that is positive, capped (e.g.
  150 ms). Video then lands at ~170 ms in shared mode (fine for calls), and nothing speeds audio up. Measuring
  the real offset needs the camera (permission) and a person, or an AV-sync clip filmed by the Mac camera.

## Surprises

1. **Chrome's performance clock drifts -25 ppm** against Windows system time. Any PC-side latency measurement
   that compares a browser frame time with another process's time over minutes must correct for it (C2's 10 s
   runs were unaffected).
2. **The playout buffer is ~80 % of the latency.** Encode + network + decode + virtual camera is ~12 ms p50;
   D = 50 ms adds ~45 ms of waiting. The adaptive rule sits at its floor almost all the time, and one Wi-Fi spike
   pins D high for ~10 s.
3. **The encoder starts in 4 ms when warm** (C1 measured 150 ms cold). On-demand start is limited by the IDR's
   pacing and the camera, not by VideoToolbox.
4. **The first IDR after start shows ~300 ms after capture** (paced at 2.5x, then shown at once). The frames
   queued behind it are late too, so the stream starts at ~300 ms latency and settles to ~57 ms within 0.3 s,
   because late frames are shown on arrival and never delay later ones.
5. **A naive pacer loses its sleep overshoot on every packet:** 0.35 ms x 105 packets made an IDR "paced at 2.5x"
   go out at 2.0x. The Phase 2 pacer must keep an absolute schedule.
6. **Windows `WSAEventSelect` events stay signalled** until reset. A first `camrecv` spun a core because of it.

## Changes for Phase 2 (vs C1-C3 recommendations)

1. **IDR pacing at 4x the bitrate** (C3 left 2.5-4x open): 0 loss in 300 IDRs at 720p and 1080p. It cuts
   start-up by 64 ms (720p) and stays well below the 25 Mbit/s that lost packets. Use an absolute schedule (no
   accumulated sleep overshoot).
2. **Show late frames on arrival** instead of C3's "decode but never show late frames". With a ring-based
   virtual camera, an older frame is never shown after a newer one, and nothing accumulates. Dropping late frames
   would turn every Wi-Fi spike into a freeze (76-110 late frames per 10 min here, 0 visible freezes). Do not hold
   an IDR to its deadline either; show it at once.
3. **Ack precisely: [clean_from, acked_frame]**, not "newest decoded" alone. After a recovery, the Mac must only
   acknowledge tokens of frames inside the current clean run, or a refresh could reference an LTR the PC never
   decoded cleanly. C1's acked-token rule needs this extra field in the video RR (C3's RR has `acked_frame` only).
4. **Start the receiver "broken" until the session's first IDR**, with the first PLI 300 ms later. Otherwise a
   lost first IDR is decoded as garbage, and an immediate PLI causes a second 120-256 KB IDR.
5. **Keep the encoder process (helper) alive across demands.** VideoToolbox stays warm (4 ms instead of 150 ms),
   as C1 recommended (video backend inside the existing helper); now measured.
6. **Playout floor as a setting.** 50 ms is C3's choice; 30 ms would save 20 ms for ~2 % late frames (judder,
   not freezes). Also consider capping how long one spike can hold D up (p99 over 10 s holds it ~10 s). Decide
   with the real camera, and with lip sync (Q5), which may want a higher D anyway.
7. **Lip sync:** delay video to match the audio path (kSr, as C3 proposed), not audio to match video. See Q5 for
   the size.
8. **Placeholder threshold:** C2's prototype source shows its placeholder after 500 ms without a frame. During
   the injected 1.5 s blackout Chrome saw ~1 s of placeholder after 0.5 s frozen. C2 recommended 250 ms; for
   80-packet losses (300 ms) 250 ms would flash the placeholder. **Keep ~500 ms** (or hold the last frame up to
   1 s).
9. **Clock offset must be tracked continuously** (10.5 ppm = 18 ms per 30 min here, and it wanders between
   runs). Deadlines computed from a start-time offset would drift out of the buffer.
10. **Firewall:** a new PC executable that binds a UDP port in the user's session gets a Windows Firewall prompt,
    and Allow rules created for it. This favours C1/C3's choice of putting video in the existing `beamer-audio.exe`,
    which already has installer rules.
11. **TCC, real camera, cold start: unchanged, still blocked** (C1). The latency budget has one unmeasured term.
