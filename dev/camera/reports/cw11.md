### Bug 1 (blocker): the Mac synthetic source waits on the wrong clock after the Mac has slept

`native/audio/mac/synth_mac.mm:274-294` (`SynthSource::run`). `due` is computed on `macvideo::now_ns()`
(`video_backend_mac.h:37`: libc++ `steady_clock`), and the last <= 3 ms of each wait is
`mach_wait_until(due)`, i.e. the same number read as **mach host time** (comment line 282: "host clock ==
now_ns()"). On Apple, libc++ `steady_clock` is `CLOCK_MONOTONIC_RAW`, which counts sleep, while
`mach_absolute_time` (`CLOCK_UPTIME_RAW`) does not. They agree only on a Mac that has never slept since boot,
which is what CW3's `video_check` selftest and CW10 saw. Tonight on this Mac:

```
steady_clock 113618.734 s, mach host 113450.950 s, steady - host = 167.785 s   (C++ check, scratch build)
CLOCK_MONOTONIC_RAW - CLOCK_UPTIME_RAW = 167.7846 s                            (Python, same)
helper stats now_ns - app mono = 167.7842 s                                    (both smoke runs, from the events)
```

So every frame's final wait is `mach_wait_until(host_now + 167.8 s)`. Effects:
1. The synthetic camera never delivers a frame within a stream's life: Mac `camera` stays `starting`,
   `cam_fps 0`, `frames 0`, `idr 0`, while PLIs arrive (`pli_rx` +10/s) and the PC shows the placeholder.
2. Stopping the stream runs `~SynthSource` -> `thread_.join()` (line 255). `mach_wait_until` cannot be
   woken by `stop_`, so the helper's control thread blocks for up to 168 s. The app's watchdog kills it after
   10 s, and the Mac camera counts as on during that time (the invariant violations above).

`5925b36` ("Mac camera: map frame PTS to the engine clock through the live offset") fixed the same
assumption in `camera_mac.mm::host_time_to_ns` for the real camera, but not in the synth source. The strip's
capture time (`synth_mac.mm:301`, `now_ns()`) is on `steady_clock` too; the harness now handles that (below).

**Proposed fix (product, not done here)**: in `synth_mac.mm`, turn the remaining wait into a host deadline
computed from the host clock, e.g. `mach_wait_until(mach_absolute_time() + ns_to_host_ticks(due - now))`.
Alternatively, drop `mach_wait_until` and use `cv_.wait_until` on `steady_clock` with the 2-3 ms margin as
spin/yield. Then fix the false comments in `video_backend_mac.h:35-36` and `synth_mac.mm:282`, and make
`video_check`'s "host == now_ns" selftest compare the two clocks' *rates*, or give it a sleep-gap tolerance,
so that it cannot pass only because the Mac never slept. Also grep the other Mac helper code for any other
`mach_*` deadline built from `now_ns()`. Until the fix is deployed, a Mac reboot makes the gap 0 and the suite
runnable, until the next sleep. Rebooting is not this WP's call.

### Bug 2: after a PC Beamer restart the Mac's flow offer can be lost, and nothing retries it

Seen after the deploy restarted the PC Beamer (19:50:46). The Mac offered flow `f3b8feb7` at Mac 19:50:47.785
(`flow_bound`, then the offer). The **PC helper never got a `flow_open` for it**: there is no `flow_bound` in
the PC events after its `ready` (19:50:46.894) and its `_link_up` (46.938), and the PC log has no `flow` line. The
Mac's flow went `probing -> link` at 19:50:49.782 and stayed unagreed for 7 min, so `flow_for()` returned None
(`core/audio/service.py:192-196`). The camera part therefore never sent `send` (`core/camera/part.py:990-992`),
while the plan said `starting` (PC sink `starting`, `streams []`). Audio over that flow would have failed the
same way. It cleared only when the PC helper restarted (`cam_helper_kill`): the Mac dropped the flow on the
helper's `starting` hello and re-offered on `ok`.

Where the offer can vanish without a log line: `_on_audio_flow` (`core/audio/service.py:828-847`) returns
silently if the peer is not yet `direct` (no `audio_hello` received yet, line 831), if the helper is not ok, or
if this side thinks it is the offerer (line 839). The hello and the offer travel on the two different TCP links
and left the Mac 29 ms apart; with the PC wall clock 0.75 s behind the Mac's (+-0.1 s), the logs cannot prove
which arrived first. Ordering across the links (offer before hello -> line 831) is the most likely cause. On
the offerer side, `want` is ignored while an own offer is pending (line 835-837), and no timer re-offers.

**Proposed fix (product)**: (a) log every dropped offer (phase, reason); (b) on the answerer, keep an offer
that arrives before the hello and process it in `_on_audio_hello`, or send `flow_want` from `_on_audio_hello`
when `state.flow is None`; (c) on the offerer, re-offer when an offer is still unanswered after ~3 s, and treat
`want` while pending as a re-offer request. Add an engine/service test that delivers `flow offer` before
`audio_hello`.
