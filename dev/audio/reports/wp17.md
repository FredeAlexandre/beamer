## 1. Low-latency render into CABLE Input for the mono mic stream
Cause (WP16 miss 1): mono into CABLE Input's stereo mix needs AUTOCONVERTPCM, which `InitializeSharedAudioStream` rejects
(0x88890021). Fix: when the engine renders **mono** into a device that has a shared period range (CABLE Input), the
stream opens at the mix (2 ch, no conversion) and `pump_render` copies mono into every channel (unity, same as WASAPI).
Log line now: `render+upmix(low-latency period 128), 2 ch from the device, 1 ch to the engine, buffer 280 frames`.
G733/DualSense have no period range: they keep WASAPI's conversion (unchanged, render-test mono/stereo at unity).
Measured with `backend_check vmic-latency --channels 1` (the mic stream as Beamer opens it; click -> app-style capture of CABLE Output):
| path | median per run (ms) | holes |
|---|---|---|
| **mono, up-mix, 128 x 3 (new)** | 79.1, 70.7, 71.5, 72.3; 300 s: **80.1** (p95 81.5) | **0 in 4x60 s + 300 s** |
| mono, old path (autoconvert, 480) same session | 89.4 | 0 in 60 s |
| stereo 128 x 3 (WP12 path) same session | 78.3 | 0 in 60 s |
Mono equals stereo 128, as expected. Medians are 70-80 ms, not WP12's 59-72: the ~10 ms spread is the phase between
the CABLE engines (WP12), and this session's old-path figure (89) is also lower than WP12's 102-117. vmic-test mono: tone -20.00 dBFS in, -20.00 out, 0 holes.
Limit: a stereo engine stream into a >2-channel CABLE mix would still ask for conversion (falls back to 480, logged); not used today.
## 2. The user's volume change wins during a redirect
`MuteManager` registers an `IAudioEndpointVolumeCallback` per held endpoint. Every write of ours (SetMute, restore)
carries a per-process event context GUID (`own_volume_context()`); any other notification is the user's. The
callback only copies the values; a watcher thread applies them under the manager's lock:
- volume (master + channels) -> new restore target; the journal is rewritten at once (guard/next start restore it);
- unmute -> left playing for the rest of the redirect (later holds of that endpoint, e.g. a second capture or a
  default move and back, do not mute; reset when nothing is held); its mute state then follows the user (re-mute -> restored muted);
- a pending change is applied before the final restore. Log: `warn: endpoint X unmuted by the user during the redirect ...`.
`backend_check user-change-test` (G733, 15/15 PASS): own-context write ignored; volume 0.80 -> 0.74 from another process
= target + journal, still muted; unmute with a foreign GUID reported at once, not re-muted (also with a 2nd capture);
later 0.77 kept at the end (not 0.80); next redirect mutes again; helper killed after a user change -> guard restores the user's 0.74.
Then put back to 0.80 exactly. vmic/system/render/journal/invalidate/exclusive tests: all PASS.
