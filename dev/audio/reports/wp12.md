## Fallbacks and one bug found
- If another stream already holds CABLE Input's engine at another period, the open falls back to the default period
  (logged as `low-latency period refused`); the log line of each stream shows `low-latency period N` or `default period N`.
- `exclusive-test` failed at first: another app's exclusive open preempts us, and its immediate retry with a second
  format got `DEVICE_IN_USE` because the low-latency stream was back after 50 ms (3/3 runs; never with 480). Fix: the
  virtual-mic stream waits 250 ms before its first reopen. Now 3/3 PASS.
- Acceptance re-run with the new defaults: vmic-test, render-test, system-test, invalidate-test, exclusive-test,
  journal-test all PASS. Engine tests 17 cases / 1886 checks / 0 failures. `beamer-audio.exe` builds (static x64).

## Task 3: exclusive render per machine (Python side, owned by core/audio)
The helper already takes `--vmic-exclusive`; `main.cpp` now keeps it out of the engine's argv (no warning), and
`ready.features` then contains `"vmic_exclusive"`. Python must: (1) keep a per-machine, never-synced setting, e.g.
`audio.json` `"local": {"aec": ..., "vmic_exclusive": false}` (§8.4); (2) `helper.command_line(..., vmic_exclusive=True)`
appends `"--vmic-exclusive"`; (3) on a change, restart the helper (no runtime command: §2.4 has no option hook; a
restart drops streams ~1 s); (4) show it as on only if `ready.features` has `vmic_exclusive`; even then the stream
falls back to shared when CABLE Input can't be opened exclusively (logged `exclusive render ... refused`).
